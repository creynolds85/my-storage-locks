# Weekly manager walk-through

Manager route: `/dashboard?view=walkthrough&facility=<authorized facility>`.

Cubby `POST /v1/units/search` documents `walkthroughOrder`; its reporting `units.walkthrough_order` also exposes the configured sequence. The live API omits the optional customer expansion on the bulk lease response, so tenant names come from the existing facility-scoped Customers Search endpoint. The new server-only refresh reads the Operator API, with current facility-scoped leases, active customer names and auction records. It stores only the minimal unit/tenant-name/expected-state projection, never contact details, balances, access credentials or combinations. Completed/cancelled auctions are excluded; active auctions take precedence over overlocks. Unverifiable occupancy is visibly blocked from normal confirmation.

Units sort by Cubby's numeric position. Tied/missing positions use natural unit-number order, with a deterministic original-label/source-ID tie break. A week's initial sequence stays fixed after inspection; new units append. The next week adopts the latest Cubby sequence. No separate route is maintained. Refresh runs on opening a facility and once per minute while its walk-through remains open; it does not change the existing automation polling worker.

Weeks begin Monday in America/New_York, matching the application's calendar convention. The current week is created lazily on the first authorized visit. Per-unit optimistic revisions plus a week row lock prevent concurrent managers from overwriting one another. Expected-condition or local-assignment changes require reinspection; every saved revision is retained privately. Sources older than five minutes block confirmation and completion. Historical weeks remain read-only.

Vacant lock requirements default to **not configured**. No missing vacant-lock warning is inferred from vacancy alone. Administrators can choose required/not required per facility. Auction security defaults to the requested auction-lock workflow; administrators can select an overlock or no facility lock where that is the actual requirement. Overlock expectations follow Cubby's current overlocked/overlock-needed flags. Local active assignments are authoritative. Missing-assignment alerts describe inventory discrepancies, not proof of physical absence. Alerts link into the existing available-lock selection and prefill the unit/type, without assigning anything automatically.

Exactly six issues are supported. Exception and missing-assignment tasks reuse the existing dashboard Action Items and resolution RPC. Issue corrections resolve the superseded issue task while retaining the observation history. Resolving tasks never deletes inspection history. Policy, roster, observation, concurrency tokens and audit data are protected by existing live-session/facility authorization. Employee screens receive only operational fields and plain errors.

Optional notes are supported. Photos are not introduced: the existing application has no photo storage/upload workflow. No Cubby writes, lock mutations, combination reads, SMS dispatch, or Twilio configuration changes are part of this feature.

Focused verification: `node --test tests/walkthrough.test.mjs`, `tests/walkthrough.acceptance.sql` (transaction rolled back), TypeScript and production build. The SQL fixtures cover weekly persistence/rollover, required-lock warnings, issue deduplication/corrections, facility permissions, attribution, stale-source refusal and simultaneous-manager revision conflicts.

## Compact mobile inspection controls

Collapsed cards use an approximately 86–100px row for ordinary unit labels, with a separate 44px issue target and 66×64px right-side confirmation button. Missing-assignment warnings and expanded issue controls may increase card height. The progress header is compact; previous weeks are under History. Next Unit is a direct action. Confirmation advances only after the server saves, follows the existing roster sequence (wrapping to earlier remaining units), and respects reduced-motion preferences. The card is not a confirmation target.

Confirmation and issues are independent. Existing legacy observations and timestamps are interpreted without rewriting their original fields; new explicit operations update only confirmation, issue, or notes. Undo changes only confirmation. A unit with a documented exception still counts as inspected, and an issue remains visible when confirmed. Issue tasks are updated only by issue/notes edits, never by confirmation or Undo. Every new change is recorded privately with manager attribution. Previous inspection records remain read-only.

Successful saves return the changed entry only. Memoized cards retain unchanged object references; no roster reload follows a successful save. One-minute source refresh and existing revision/eligibility checks remain in place. Collapsed cards use browser content visibility to reduce painting work on long rosters. The latest confirmation can be undone from the persistent accessible feedback bar or the unit's confirmation button.

Focused checks for this update: `tests/walkthrough-speed.test.mjs`, `tests/walkthrough-card.test.mjs`, and rollback-only `tests/walkthrough-speed.acceptance.sql`. Browser-based visual measurement is limited by the execution environment's Chromium socket restrictions; rendered card contracts, touch-target CSS, navigation logic, database persistence and production compilation are checked separately.

## Quick Walk and virtualized Review

Quick Walk is the default for the current inspection. It renders at most ten unconfirmed entries in the original persisted Cubby order, automatically replenishing the queue after an acknowledged confirmation. An issue-only row remains available to confirm independently; existing completion/progress rules still count documented exceptions as inspected. No bulk confirmation is provided. Standard rows are 80px tall with neutral 56px confirmation targets and separate 44px issue buttons. Compact warning chips reuse the existing assignment action without making assignments automatically.

A row remains present while its save is pending or fails. A synchronous per-unit gate drops repeated confirmation taps while the existing mutation queue serializes intentional notes, issue and confirmation edits. Successful saves patch only the returned entry. A short exit animation removes the confirmed row without scrolling the viewport; reduced-motion users receive an immediate transition. Undo returns the entry to its original queue position and changes only confirmation. The fixed-height scroll region keeps controls stable as the queue replenishes.

Review renders all entries through a fixed-pitch virtual window with overscan, rather than mounting 500–1,000 cards. Next Unchecked scrolls directly to the next remaining entry. Mode switches retain the same in-memory inspection and never refetch or reset progress. History opens in read-only Review. The six issue choices and optional notes are in a native modal sheet; they use the existing independent field operations and dashboard Action Items. Failed notes keep the draft available to retry. No database, authorization, source ordering, Cubby mirror, inventory or SMS changes are included.

Focused UI checks use 1,000 isolated records and a controlled RPC client in Happy DOM. The test-only dependency is installed outside the application (no production dependency or lockfile change): `npm install --prefix /tmp/msl-walk-ui --no-save --package-lock=false --ignore-scripts happy-dom@21.0.4`, then `WALK_DOM_MODULE=/tmp/msl-walk-ui/node_modules/happy-dom/lib/index.js node --test tests/quick-walk-ui.test.mjs`. The tests cover queue replenishment, duplicate prevention, save failures, Undo, both issue/confirmation orders, notes/retry, mode switches, virtualized ordering, History, assignment links, reduced motion and CSS touch-target contracts. These are DOM and CSS checks, not a physical-device visual certification.
