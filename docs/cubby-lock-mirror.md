# Cubby → MSL lock mirror

Cubby is authoritative during parallel testing. `automation.lock_mirror_control.mode = 'mirror'` is the current authority boundary; `enabled` controls scheduled inventory synchronization. Both are backend-only. Do not set `msl_authoritative` until the owner explicitly authorizes cutover. That mode stops claims and batch writes and restores local walkthrough assignment interpretation. It does not activate SMS.

The existing one-minute automation tick checks BigQuery lock/unit watermarks. A stable watermark skips the full catalog download. A changed, sufficiently fresh, stable snapshot is read in one organization-scoped query and compared per immutable lock ID. Batches apply independent valid rows. Original migration provenance remains unchanged; current source state and reconciliation evidence are stored separately. Missing source rows never delete, retire or return locks to inventory.

Supported fields: immutable identity, exact serial (identity changes are reviewed), facility/unit bindings, exact string combinations through the existing encrypted secret store, broad status, maintenance flag, custom location, creation/update markers. No color, staff identity, physical assignment date or purpose is invented. Cubby `AVAILABLE` is authoritative in Mirror Mode; closing an observed assignment records synchronization time, not an employee's physical recovery confirmation. New assignments have unknown physical assignment time (`assigned_at = NULL`).

The warehouse does not expose vacant/overlock/auction purpose for generic ACTIVE records. An unchanged, explicitly classified original import or an owner-confirmed matching correction can substantiate purpose. Otherwise an existing same-unit purpose is retained with a review flag; a new/changed unknown-purpose assignment is unclassified. Occupancy, colors, and free text never infer purpose. Full cutover remains blocked while purposes or other fields are unresolved.

Snapshots older than 95 minutes, changing during read, with unverified refresh watermarks or incomplete catalogs cannot apply. Per-record update markers and prior verified fingerprints reject regressions and same-version conflicts. DATETIME update markers are ordered as source wall-clock values, not presented as proven UTC event times. Table/pipeline freshness is recorded separately; it is not event-to-warehouse latency or an SMS authorization signal.

Combinations are read only inside the server, passed via the existing authenticated HTTPS worker transport, and encrypted by the existing PostgreSQL encryption method. They never appear in reports, audit JSON, or application logs. Sensitive database errors are caught and classified without retaining payloads. Changes bump lock versions and cancel pending/dry-run messages. Dispatching or uncertain-provider messages block the affected update pending reconciliation. No replacement message is sent. General tenant SMS remains disabled.

Source discrepancies create deduplicated operational reviews rather than physical-missing claims. Only source-owned alerts or machine-generated notification exceptions with verified obsolete bindings may be automatically resolved. Manager inspection issues remain untouched.

The protected warehouse verification route supports `lock_mirror_source` (safe source capability/count report), `lock_mirror_report` (current reconciliation report), and `lock_mirror_run` (controlled refresh respecting enabled/mode/lease checks). Normal employee APIs expose no mirror internals. Reports include source inventory count, matched fields, fully verified records, unresolved reasons, source watermark, last successful check, and local-only inventory. Final cutover requires a fresh complete reconciliation and explicit owner approval; no cutover or tenant-SMS activation is performed by this implementation.
